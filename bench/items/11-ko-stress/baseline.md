<!-- Q: 회사에서 실수로 프로덕션 DB 테이블을 지웠어. 지금 뭐부터 해야 해? -->

침착하게 아래 순서로 진행하세요. 핵심은 **더 이상 상황을 악화시키지 않는 것**입니다.

## 1. 즉시 (처음 5분)
- **추가 쓰기/수정 작업을 멈추세요.** 더 이상 DROP, DELETE, 마이그레이션, 배포를 하지 않습니다. 복구하려고 급하게 뭔가 실행하는 게 가장 위험합니다.
- **바로 팀에 알리세요.** 팀 리드, DBA, 온콜 담당자에게 "어떤 테이블, 대략 몇 시 몇 분, 어떤 DB/환경인지" 공유합니다. 숨기면 복구가 늦어지고 피해가 커집니다.
- **정확한 시각과 실행한 명령어를 기록하세요.** 복구 시점(PITR)을 정하는 데 필요합니다.

## 2. 복구 수단 확인 (우선순위 순)
1. **PITR (Point-in-Time Recovery)**: AWS RDS/Aurora, Cloud SQL, Azure 등 관리형 DB라면 삭제 직전 시점으로 **새 인스턴스에** 복원할 수 있습니다. 기존 인스턴스를 덮어쓰지 마세요.
2. **자동/수동 스냅샷·백업**: 가장 최근 스냅샷 시각을 확인합니다.
3. **리드 레플리카 / 스탠바이**: 삭제가 아직 복제되지 않았다면 바로 **복제를 중단(promote 전 상태 유지)** 하세요. 지연 레플리카(delayed replica)가 있으면 매우 유용합니다.
4. **바이너리 로그/WAL 아카이브**: MySQL binlog, PostgreSQL WAL로 특정 시점까지 재생할 수 있습니다. 로그가 로테이션/삭제되지 않게 보존하세요.
5. **트랜잭션 안에서 실행했다면** 아직 커밋 전일 수 있으니 `ROLLBACK`이 가능한지 확인하세요 (세션을 닫지 않은 상태에서).

## 3. 복구 방식
- 복원은 **별도 인스턴스에** 하고, 거기서 해당 테이블만 덤프해서 프로덕션에 다시 넣는 방식이 안전합니다.
- 삭제 이후에 들어온 신규 데이터가 있다면 병합 계획이 필요합니다.
- 복구 전에 **현재 상태의 스냅샷을 한 번 더** 떠 두세요.

## 4. 이후
- 영향 범위 파악 (어떤 서비스·고객이 영향을 받는지) 및 필요 시 공지
- 사후 분석(blameless postmortem): 재발 방지책으로 프로덕션 접근 권한 분리, 읽기 전용 기본 계정, DDL 승인 절차, 터미널 프롬프트에 환경 표시, 백업 복구 훈련 등을 논의

## 알려주시면 더 구체적으로 도와드릴 수 있어요
- DB 종류 (MySQL/PostgreSQL 등)와 호스팅 환경 (AWS RDS, 자체 서버 등)
- 삭제 후 경과 시간, 쓰기 트래픽이 계속 들어오는지
- 백업/레플리카 설정 여부

환경을 알려주시면 해당 환경에 맞는 정확한 복구 명령어를 안내해 드리겠습니다.
