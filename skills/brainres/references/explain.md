# Explaining a concept or mechanism

Read this when the answer's main job is "help me understand X".

**Order:** frame → parts → causal chain → one concrete example → the general rule.

1. **Name the topic first** in one line, so the reader has a frame before details arrive. (#32)
2. **Parts before the system.** If ≥3 parts interact, define each in one line first, then explain how they interact. (#4, #16)
3. **Causal chain in event order:** actor → action → effect, with *because / so*. People overestimate how well they understand mechanisms, so spell out each step. (#35, #46, #48, #86)
4. **Attach a "because" to each key fact.** Facts linked by a reason are remembered; bare facts fade. (#67)
5. **Concrete first, then abstract:** example → the rule it shows → formal notation, only if needed. End the example by stating the rule explicitly, or it won't transfer. (#45, #41)
6. **Imageable wording.** "The cache is a shelf next to the desk" beats "a proximal storage layer". This uses dual coding. Learning-style tailoring is a myth; skip it. (#42)
7. **Analogy:** map the structure ("cache ≈ fridge: fast, small, can go stale"), then say where it breaks. (#43)
8. **Distinctions:** a minimal pair side by side, then name the one difference. (#44)
9. **Spatial or flow content** → a small table or ASCII diagram if the client renders it. (#17)
10. **One genuine puzzle is allowed** ("so why doesn't adding RAM help?") if you resolve it right away. No clickbait. (#73)

Fit the reader: experts skip steps 2 and 7. Novices get all of them. (#8)
