# 역할 기반 권한(RBAC) 구현 계획

현재 코드를 보지 않은 상태라 아래는 일반적인 가정에 기반한 계획입니다. 가정: 인증은 Django `User`, 관리자 페이지는 Django Admin 또는 DRF + 별도 프론트.

## 1. 설계 결정

**권장안: Django 내장 `Group` + `Permission` 활용**
- 역할 3개를 Group(`admin`, `editor`, `viewer`)으로 만들고, 각 Group에 모델 권한(`view_`, `add_`, `change_`, `delete_`)을 부여합니다.
- 장점: 추가 테이블 없음, Django Admin과 DRF가 바로 연동, 검증된 구조.
- 사용자당 역할은 1개로 제한합니다(코드/데이터 마이그레이션으로 보장).
- 커스텀 필드 방식(`User.role` Enum)은 권한이 "역할 단위로 단순"하고 객체 단위 권한이 필요 없을 때만 고려합니다.

| 역할 | 조회 | 생성 | 수정 | 삭제 | 사용자/권한 관리 |
|---|---|---|---|---|---|
| admin | O | O | O | O | O |
| editor | O | O | O | X | X |
| viewer | O | X | X | X | X |

## 2. 단계별 작업

### 단계 1: 권한 매트릭스 확정
- 관리 대상 모델/화면 목록을 뽑고 위 표를 모델별로 구체화합니다.
- 모델별 예외(예: editor가 `AuditLog`는 조회 불가)를 이 단계에서 결정합니다.

### 단계 2: 역할/권한 데이터 마련
- 역할 정의를 코드 한 곳(`accounts/roles.py`)에 상수로 둡니다.
  ```python
  ROLE_PERMISSIONS = {
      "viewer": ["view"],
      "editor": ["view", "add", "change"],
      "admin":  ["view", "add", "change", "delete"],
  }
  ```
- **data migration** 또는 `post_migrate` 시그널로 Group 생성과 권한 할당을 수행합니다. 멱등하게 작성하여 배포 때마다 안전하게 재실행되도록 합니다.
- 새 모델이 추가될 때 권한이 자동 반영되도록 `manage.py sync_roles` 커맨드도 제공합니다.

### 단계 3: 기존 사용자 마이그레이션
- 현재 사용자들의 역할 매핑표(CSV 등)를 받아 data migration으로 적용합니다.
- 매핑이 없는 사용자는 기본 **viewer**로 두는 최소 권한 원칙을 적용합니다.
- `is_superuser`는 소수 운영자에게만 남기고, 일반 admin 역할과 분리합니다.

### 단계 4: 서버 측 강제 (가장 중요)
- **Django Admin인 경우**: `ModelAdmin`이 `has_view/add/change/delete_permission`을 Django 권한 기반으로 판단하므로 대부분 자동 적용됩니다. `is_staff=True` 설정이 필요하고, 공통 `BaseModelAdmin`을 만들어 모든 Admin이 상속하게 합니다.
- **커스텀 뷰/DRF인 경우**:
  - DRF: `DjangoModelPermissions` 기반 permission class를 기본값(`DEFAULT_PERMISSION_CLASSES`)으로 설정합니다. `GET`에도 `view` 권한을 요구하려면 `get_queryset`/`perms_map`을 오버라이드합니다.
  - 일반 뷰: `PermissionRequiredMixin` / `@permission_required`.
- 기본값을 "거부"로 두어, 권한 설정을 빠뜨린 뷰가 열려 있지 않게 합니다.
- 사용자/역할 변경 화면은 admin만 접근 가능하게 하고, **자기 자신의 역할 변경 및 마지막 admin 강등을 차단**합니다.

### 단계 5: 프론트엔드 반영 (별도 SPA인 경우)
- `/api/me/`에 `role`과 `permissions` 목록을 반환합니다.
- 버튼/메뉴 노출은 이 값으로 제어하되, **UI 숨김은 편의일 뿐 보안은 서버에서 보장**합니다.
- 권한 없음은 403으로 응답하고 프론트에서 일관되게 처리합니다.

### 단계 6: 감사 로그
- 역할 변경, 권한 거부(403), 삭제 같은 민감 작업을 기록합니다(`django-simple-history` 또는 `LogEntry` 활용).
- 누가 누구의 역할을 언제 바꿨는지 추적 가능해야 합니다.

### 단계 7: 테스트
- 역할 × 엔드포인트/Admin 액션 매트릭스를 `pytest.mark.parametrize`로 테스트합니다.
- 필수 케이스:
  - viewer의 쓰기 시도 → 403
  - editor의 삭제 시도 → 403
  - 비인증 접근 → 401/302
  - 역할 변경 직후 권한 반영 (권한 캐싱 주의)
  - 마지막 admin 강등 방지
  - `sync_roles` 멱등성
- 새 뷰가 권한 클래스 없이 추가되면 실패하는 가드 테스트(URL 전체 순회)를 하나 둡니다.

### 단계 8: 배포 및 롤아웃
1. 마이그레이션 먼저 배포 (Group/권한 생성, 사용자 매핑). 이 시점에는 강제 적용 없음.
2. 권한 검사를 **로그만 남기는 모드**로 짧게 운영해 오탐(정상 사용자 차단)을 확인합니다.
3. 강제 적용으로 전환합니다.
4. 롤백 계획: 기본 권한 클래스 설정을 이전으로 되돌리면 복구되도록 feature flag(환경변수)로 감쌉니다.

## 3. 주의할 점
- Django는 사용자 권한을 요청 간 캐싱하므로, 역할 변경 후 같은 요청 내에서는 반영되지 않을 수 있습니다.
- `is_superuser`는 모든 권한 검사를 우회하므로 사용 범위를 최소화합니다.
- 행 단위 권한(자기 부서 데이터만 편집 등)이 필요해지면 `django-guardian`이나 queryset 필터링을 별도 검토합니다. 이번 범위에서는 제외합니다.
- 대시보드/집계 API처럼 모델 권한에 매핑되지 않는 화면은 커스텀 권한(`Meta.permissions`)을 정의합니다.

## 4. 예상 일정 (1인 기준)
- 단계 1–3: 1~2일
- 단계 4–5: 2~3일
- 단계 6–7: 2일
- 단계 8: 1일 (모니터링 기간 별도)

## 5. 확인이 필요한 질문
1. 관리자 페이지가 **Django Admin**인가요, 아니면 DRF + 별도 프론트인가요?
2. 한 사용자가 여러 역할을 가질 수 있어야 하나요?
3. 모델별/필드별 예외 권한이 있나요?
4. 인증이 SSO/LDAP 등 외부 연동인가요? 그렇다면 역할을 IdP 그룹에서 매핑할지 결정이 필요합니다.
