<!-- Q: What makes a good README? -->

A good README answers a newcomer's questions in the order they ask them.

**1. What is this? (first few lines)**
- One-sentence description of what the project does and who it's for.
- Optionally a screenshot, GIF, or short code sample showing it in action.

**2. How do I get started?**
- Prerequisites (language versions, OS, dependencies).
- Install steps that can be copy-pasted.
- A minimal working example. A reader should reach "it works" in under five minutes.

**3. How do I use it?**
- Common use cases with examples, not exhaustive API docs. Link out to fuller docs if they exist.
- Configuration options, flags, or environment variables that matter.

**4. How do I contribute or get help?**
- Link to CONTRIBUTING, the issue tracker, or chat/discussion channels.
- How to run tests and build locally.

**5. Housekeeping**
- License (essential; without one, others can't legally reuse the code).
- Maintainers or contact, changelog link, acknowledgments.

**Qualities that matter more than sections**
- **Skimmable:** clear headings, short paragraphs, code blocks for anything typed.
- **Accurate:** commands actually work on a clean machine. Stale instructions are worse than none.
- **Scoped:** the README is the front door, not the whole house. Move deep material to `docs/`.
- **Honest:** state status (alpha, stable, maintained), known limitations, and what the project is *not*.
- **Written for a stranger:** avoid insider jargon and assume no prior context.

**Common mistakes**
- Leading with history, philosophy, or a table of contents instead of what the project does.
- Install steps that skip prerequisites.
- Badge walls that bury the content.
- Examples that can't be run as written.

A useful test: hand it to someone unfamiliar with the project and see whether they can install and run it without asking you anything.
