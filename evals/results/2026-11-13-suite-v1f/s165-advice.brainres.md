<!-- Q: What makes a good README? -->

A good README lets a stranger decide in 30 seconds whether the project is for them, then get it running in five minutes.

Include these four things, in this order:

1. **What and why:** one or two sentences on what the project does and who needs it. Add a screenshot, GIF, or short output sample if it's visual or a CLI.
2. **Quick start:** the shortest path from zero to a working result. Give copy-pasteable commands, plus the prerequisites and versions they need.
3. **Usage:** one or two realistic examples, then a link to full docs instead of listing every option.
4. **Contributing and license:** how to run tests, where to file issues, and which license applies.

Keep it honest and current. A README with a command that no longer works costs more trust than a short one. Test your quick start on a clean machine or fresh clone, because you will miss steps you've done so often you forgot them.

Skip long histories, exhaustive API references, and badge walls. Move those to a `docs/` folder or a wiki.
