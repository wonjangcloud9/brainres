<!-- Q: OAuth랑 JWT 차이가 뭐예요? -->

**한 줄 요약:** OAuth는 "권한 위임 프로토콜(절차)"이고, JWT는 "토큰 형식(포맷)"입니다. 비교 대상이 아니라 서로 다른 층위의 개념이라 함께 쓰이는 경우가 많습니다.

## OAuth (2.0)
- **목적:** 제3자 앱이 사용자의 비밀번호 없이 특정 리소스에 접근할 수 있도록 **권한을 위임**하는 프레임워크
- **구성:** 사용자(Resource Owner), 클라이언트 앱, 인증/인가 서버, 리소스 서버
- **예:** "Google로 로그인", "GitHub 저장소 접근 허용"
- **흐름:** Authorization Code, Client Credentials 등 여러 grant type으로 액세스 토큰을 발급받는 절차를 정의
- 토큰이 **어떤 형태여야 하는지는 규정하지 않음** (랜덤 문자열이어도 됨)

## JWT (JSON Web Token)
- **목적:** 클레임(정보)을 JSON으로 담아 **서명**한 토큰 포맷 (RFC 7519)
- **구조:** `header.payload.signature` (Base64URL 인코딩)
- **특징:** 자체 포함(self-contained). 서버가 DB 조회 없이 서명만 검증해 사용자 정보와 만료 시간 등을 확인 가능
- 인증 방식과 무관하게 쓸 수 있음 (세션 대신 쓰는 자체 로그인, 서비스 간 통신 등)

## 주요 차이

| 구분 | OAuth 2.0 | JWT |
|---|---|---|
| 정체 | 인가 프레임워크/프로토콜 | 토큰 포맷 |
| 해결하는 문제 | 누가 누구에게 어떤 권한을 줄지 | 정보를 안전하게 담아 전달·검증 |
| 토큰 형태 | 규정 없음 | JSON + 서명 |
| 단독 사용 | 토큰 발급 절차 자체 | 발급 절차는 별도로 필요 |

## 함께 쓰는 방식
OAuth 2.0의 액세스 토큰을 **JWT 형태로 발급**하는 경우가 흔합니다. 또한 OAuth 위에 얹은 인증 계층인 **OpenID Connect(OIDC)**의 ID Token은 JWT를 사용하도록 규정되어 있습니다.

## 참고할 점
- JWT는 서명되었을 뿐 **암호화된 게 아니므로** payload는 누구나 디코딩해 볼 수 있습니다. 민감 정보는 넣지 마세요.
- JWT는 발급 후 즉시 폐기하기 어렵기 때문에, 만료 시간을 짧게 하고 리프레시 토큰을 병행하는 것이 일반적입니다.
- OAuth는 원래 **인가(Authorization)** 용도이고, 로그인(인증)이 목적이면 OIDC를 쓰는 것이 맞습니다.
