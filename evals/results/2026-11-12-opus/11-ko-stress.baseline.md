<!-- Q: 회사에서 실수로 프로덕션 DB 테이블을 지웠어. 지금 뭐부터 해야 해? -->

당황스럽겠지만, 지금은 **빠르고 침착하게** 움직이는 게 가장 중요해요. 순서대로 진행하세요.

## 1. 손 멈추기 (지금 당장)
- **추가 명령을 실행하지 마세요.** 특히 같은 이름으로 테이블을 다시 만들거나 마이그레이션을 돌리면 복구가 더 어려워질 수 있어요.
- **아직 트랜잭션 안이라면 `ROLLBACK`부터 시도하세요.** PostgreSQL은 DDL도 트랜잭션으로 묶이니, `BEGIN` 후 실행했고 아직 커밋하지 않았다면 되돌릴 수 있어요. (MySQL의 `DROP`/`TRUNCATE`는 자동 커밋이라 해당되지 않아요.)
- 터미널 창을 닫지 마세요. **실행한 정확한 명령어와 시각(초 단위까지)**을 기록해 두세요. 시점 복구(PITR) 때 이 시각이 기준이 돼요.

## 2. 바로 보고하기
- 팀장, DBA, 온콜 담당자에게 **지금 바로** 알리세요. 숨기거나 혼자 해결하려다 시간이 지나면 복구 가능한 시간 범위(binlog/WAL 보존 기간 등)를 놓칠 수 있어요.
- 이렇게 전달하면 돼요: "○시 ○분에 ○○ DB의 ○○ 테이블을 실수로 DROP(또는 DELETE)했습니다. 추가 조치는 하지 않았습니다."
- 빨리 보고하는 게 지금 할 수 있는 가장 책임감 있는 행동이에요.

## 3. 복구 수단 확인 (DB 종류별)
| 환경 | 확인할 것 |
|---|---|
| **AWS RDS / Aurora** | 자동 백업 + 시점 복구(PITR), Aurora Backtrack |
| **GCP Cloud SQL / Azure** | PITR 기능 |
| **Oracle** | `FLASHBACK TABLE 이름 TO BEFORE DROP` (휴지통에 남아 있을 수 있음) |
| **Snowflake** | `UNDROP TABLE` |
| **BigQuery** | 타임트래블로 최대 7일 전 상태 복원 가능 |
| **자체 운영 MySQL/PostgreSQL** | 최신 백업 + binlog/WAL로 삭제 직전 시점까지 복구 |
| **지연 복제본(delayed replica)** | 있다면 즉시 복제를 중지해서 보존 |

> ⚠️ 일반 복제본에는 보통 DROP이 이미 반영돼 있어요. 그리고 **백업은 운영 DB에 덮어쓰지 말고 별도 인스턴스에 복원한 다음** 해당 테이블만 옮기는 게 안전해요.

## 4. 영향 범위 파악
- 이 테이블을 쓰는 서비스에서 지금 에러가 나고 있는지 확인하세요.
- 필요하면 점검 모드로 전환하거나 쓰기를 막아서 데이터 불일치가 생기지 않게 하세요.

## 5. 수습 후
- 포스트모템을 작성하세요. 개인 탓이 아니라 "왜 프로덕션에서 이런 명령이 가능했나"를 따지는 게 핵심이에요. 권한 분리, 확인 절차, 백업 검증 같은 개선으로 이어지면 돼요.
