<!-- Q: 회사에서 실수로 프로덕션 DB 테이블을 지웠어. 지금 뭐부터 해야 해? -->

먼저 DB에 대한 모든 쓰기를 멈추고, 지금 바로 팀 리드나 온콜 담당자에게 알리세요. 쓰기가 계속되면 로그와 백업의 복구 지점이 밀려서 복구가 어려워져요. 빨리 알릴수록 복구 확률이 높아요.

**지금 할 일 (순서대로)**

1. **트랜잭션이 아직 열려 있는지 확인해요.** PostgreSQL에서 `BEGIN` 안에서 `DROP`했고 아직 커밋 전이면 `ROLLBACK;`으로 끝나요. MySQL은 DDL이 롤백되지 않아요.
2. **복제본이 있으면 복제를 멈춰요.** 지연 복제본(delayed replica)에는 `DROP`이 아직 전달되지 않았을 수 있어요. 여기서 테이블을 건질 수 있어요.
3. **복구 수단을 찾아요.** 자동 백업, 스냅샷, PITR(RDS, Cloud SQL 등), 바이너리 로그나 WAL을 확인해요.
4. **기록을 남겨요.** `DROP` 실행 시각, 실행한 명령, 대상 DB를 적어 두세요. 복구 시점을 정할 때 필요해요.

**복구할 때 주의할 점**

프로덕션에 바로 덮어쓰지 마세요. 새 인스턴스에 `DROP` 직전 시점으로 복원하고, 그 테이블만 덤프해서 프로덕션에 다시 넣어요. 이렇게 하면 `DROP` 이후에 쌓인 데이터를 잃지 않아요.

**사고 후처리**

복구가 끝나면 원인을 공유하세요. 실수 자체보다 재발 방지 장치(프로덕션 계정 권한 분리, `DROP` 전 확인 절차)가 더 중요하게 평가돼요.

DB 종류(PostgreSQL, MySQL 등)와 호스팅 환경(RDS, 직접 운영 등)을 알려주세요. 그러면 그 환경에 맞는 복구 명령을 바로 정리해 드릴게요.
