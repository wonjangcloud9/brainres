<!-- Q: 회사에서 실수로 프로덕션 DB 테이블을 지웠어. 지금 뭐부터 해야 해? -->

먼저 **추가 작업을 멈추고**, 바로 팀에 알리세요. 복구 가능성은 처음 몇십 분에 크게 갈려요.

### 1. 손 떼기 (지금 당장)
- 명령을 더 실행하지 마세요. 혼자 복구를 시도하지도 마세요.
- DROP을 실행한 정확한 시각을 적어두세요. 셸 히스토리나 쿼리 로그에 남아 있어요. 이 시각이 복구 기준점이에요.

### 2. 즉시 보고
- 상사, DBA, 온콜 담당에게 지금 알리세요. 숨기면 복구 시간을 잃어요.
- 어떤 테이블을, 언제, 어떤 명령으로 지웠는지 그대로 전달하세요.

### 3. 복구 재료 지키기
- 자동 백업 보존 기간을 확인하세요. 오래된 스냅샷은 자동으로 지워질 수 있어요.
- 일반 레플리카도 DROP을 똑같이 복제해요. 지연 레플리카가 있으면 복제를 바로 멈추세요.
- binlog나 WAL 파일이 정리되지 않게 막으세요.

### 4. 복구 경로
| 환경 | 복구 수단 |
|---|---|
| AWS RDS/Aurora, Cloud SQL | 특정 시점 복구(PITR)로 DROP 직전 시각 지정 |
| MySQL / PostgreSQL 직접 운영 | 마지막 백업 + binlog/WAL을 DROP 직전까지 재생 |
| Snowflake, BigQuery, Oracle | `UNDROP TABLE`, 타임 트래블, `FLASHBACK TABLE ... TO BEFORE DROP` |

- 복구는 **새 인스턴스**에서 하세요. 운영 DB를 덮어쓰면 그 사이 쌓인 데이터까지 잃어요.
- 복구한 뒤 해당 테이블만 운영 DB로 옮기세요.

수습이 끝나면 사람 탓보다 재발 방지 중심으로 회고하면 돼요.

지금 어떤 DB(MySQL, PostgreSQL, RDS 등)를 쓰는지 알려주세요. 그 환경에 맞는 정확한 복구 명령을 같이 짜드릴게요.
