<!-- Q: 회사에서 실수로 프로덕션 DB 테이블을 지웠어. 지금 뭐부터 해야 해? -->

침착하게, 순서대로 하세요.

**1. 지금 당장 (5분 내)**
- **추가 명령을 실행하지 마세요.** 특히 테이블을 다시 만들거나 마이그레이션을 돌리지 마세요.
- **트랜잭션이 아직 열려 있는지 확인하세요.** `BEGIN` 후 `DROP`했고 아직 커밋 전이라면 `ROLLBACK`으로 끝납니다. Postgres는 DDL도 롤백되지만, MySQL은 DDL이 자동 커밋되어 안 됩니다.
- **팀장, DBA, 온콜에게 바로 알리세요.** 숨기면 복구가 늦어지고 피해만 커집니다. 빨리 알릴수록 복구 선택지가 많습니다.
- 가능하면 해당 테이블에 쓰기가 들어가는 서비스나 워커를 잠시 멈추거나 점검 모드로 전환하세요. 복구 시점 이후 데이터 불일치를 줄이기 위해서입니다.

**2. 복구 수단 확인 (우선순위 순)**
1. **PITR (특정 시점 복구):** RDS, Aurora, Cloud SQL 등 관리형 DB라면 DROP 직전 시점으로 **새 인스턴스**에 복구합니다.
2. **최근 스냅샷/백업:** 자동 백업이나 수동 스냅샷을 확인하세요.
3. **WAL/binlog 재생:** 백업에 더해 로그로 DROP 직전까지 따라잡습니다.
4. **레플리카:** 지연 레플리카(delayed replica)가 있다면 복제를 즉시 중단하세요. 아직 DROP이 전파되지 않았을 수 있습니다.
5. **그 외:** 데이터 웨어하우스, 분석용 복제본, 최근 export나 덤프 파일도 확인하세요.

**3. 복구 원칙**
- **프로덕션 위에 바로 덮어쓰지 마세요.** 별도 인스턴스에 복구하고 데이터를 검증한 뒤, 해당 테이블만 `pg_dump -t` 또는 `mysqldump`로 프로덕션에 옮기세요.
- DROP 시각, 실행한 쿼리, 접속한 환경과 계정을 메모해 두세요. 복구 시점 지정과 사후 분석에 필요합니다.
- DROP 이후 들어온 쓰기는 별도로 보정해야 할 수 있습니다.

**4. 복구 후**
- 사후 분석(blameless postmortem)을 하세요. 프로덕션 직접 접속 권한 분리, 읽기 전용 기본 계정, 위험 쿼리 확인 프롬프트, 백업 복구 훈련 같은 재발 방지책을 논의하세요.

어떤 DB(Postgres, MySQL 등)를 쓰고, 관리형(RDS 등)인지 직접 운영하는지 알려주세요. 그러면 맞는 구체적인 복구 명령을 단계별로 안내하겠습니다. 로컬에 있는 파일이나 스크립트를 보는 것도 도울 수 있지만, 프로덕션에 직접 명령을 실행하는 건 확인받고 진행하겠습니다.
